## User Story

### US-110: Final routing and audience-specific notifications

As a municipal case operator
I want an eligible case routed exactly once to an active authoritative unit,
with separately persisted user and target-unit notifications
So that the responsible unit receives actionable context without exposing
internal details to the applicant.

F-05 consumes stable F-02 department/unit/request-type IDs and F-03's current
completion state. Routing is deterministic from authoritative registry data;
Jamba cannot choose or replace a target unit. A notification-generation
failure cannot reverse a persisted successful routing decision.

## Gherkin Acceptance Criteria

Feature: F-05 final routing and audience-specific notifications

  Scenario: An eligible case is routed exactly once to its active target unit
    Given a case has a valid hierarchical F-02 classification
    And its F-03 completion status is `complete`
    And the authoritative routing registry marks the target unit active
    When the approved F-05 routing operation runs for its current revision
    Then it persists one routing record with `routing_status: routed`
    And its target department/unit IDs agree with the authoritative routing registry
    And a replay cannot create a second logical routing decision

  Scenario: User and target-unit notifications remain separate records
    Given a case was successfully routed
    When notification generation runs
    Then it persists an applicant-facing process notification without internal metadata
    And it persists a target-unit notification containing the approved operational context
    And either notification record can be observed independently of routing state

  Scenario: Ineligible or inactive routing targets are rejected without a route
    Given a case is `needs_review`, has F-03 missing/invalid information, or has an inactive target unit
    When the approved F-05 routing operation is requested
    Then it rejects the operation with a machine-readable error
    And it creates no routing record or notification-generation job

  Scenario: A notification failure preserves a successful route
    Given a routing record is `routed`
    And Jamba notification generation has a transient failure
    When the notification attempt fails
    Then the routing record remains `routed`
    And the notification has a retryable failed state without publishing partial text
