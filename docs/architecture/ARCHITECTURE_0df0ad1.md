# Architecture Session — US-106 F-01 intake and durable state

> Linked from [ARCHITECTURE.md](ARCHITECTURE.md). This session consumes the
> approved US-106 requirements in [DESIGN.md](../design/DESIGN.md).

## Data Models

### Entity: IntakeRequestV2

Traces to: US-106 (docs/design/DESIGN.md)

| Field | Type | Unit | Constraints |
|---|---|---|---|
| `schemaVersion` | literal string | protocol version | Required; exactly `2.0`. |
| `requestId` | opaque string | request identity | Required, non-empty; trace only, not the idempotency key. |
| `documentId` | opaque string | document identity | Required, non-empty; stable idempotency key. |
| `sourceType` | enum | — | Required; `text` or `ocr`. |
| `text` | UTF-8 string | Unicode code points | Required; its normalized form must contain at least 40 code points. |
| `sourceMetadata` | JSON object | — | Optional; defaults to `{}` and is persisted verbatim as JSONB. |
| `correlationId` | nullable string | correlation identity | Optional; retained for traceability. |

**Invariants** (must always hold true):

- `documentId` identifies exactly one persisted intake record.
- `requestId` never changes the idempotency outcome.
- Replay equality compares `sourceType`, original text, normalized text,
  `sourceMetadata`, and `correlationId`; it excludes only `requestId`.
- Both `text` and `ocr` inputs create the same downstream normalized-document
  shape; `sourceType` is audit data, not a downstream branching instruction.

**Boundary Behavior:**

- Min/Max: normalized text lengths 39, 40, and 41 code points yield reject,
  accept, and accept respectively; no maximum is introduced by this story.
- Empty/Null/Zero: missing, null, empty, or whitespace-only text returns a
  standard validation error and persists nothing.
- Overflow/Truncation: text is never silently truncated. Unsupported source
  types and non-object metadata return validation errors.
- Identity collision: changed immutable input with an existing `documentId`
  returns HTTP 409 and a non-retryable standard error; it persists nothing.

**Concurrency / Race-Scenario Analysis:**

- Concurrent submissions with the same `documentId` serialize at the database
  unique key. Equal persisted input replays the canonical result; different
  immutable input returns a 409 conflict and never overwrites the original
  record.

### Entity: IntakeRecord

Traces to: US-106 (docs/design/DESIGN.md)

| Field | Type | Unit | Constraints |
|---|---|---|---|
| `document_id` | PostgreSQL `text` | document identity | Primary key; copied from `documentId`. |
| `case_id` | UUID | case identity | Required; generated once and immutable. |
| `workflow_id` | UUID | workflow identity | Required; generated once and immutable. |
| `source_type` | PostgreSQL enum | — | Required; `text` or `ocr`. |
| `original_text` | PostgreSQL `text` | Unicode code points | Required; immutable audit source. |
| `normalized_text` | PostgreSQL `text` | Unicode code points | Required; normalized and length-validated. |
| `source_metadata` | PostgreSQL `jsonb` | — | Required; defaults to `{}`. |
| `correlation_id` | nullable PostgreSQL `text` | correlation identity | Optional. |
| `ingest_status` | enum | — | Required; `queued` after a committed initial intake. |
| `created_at`, `updated_at` | `timestamptz` | UTC instant | Required; database-generated. |

**Invariants** (must always hold true):

- Original and normalized texts, case identity, workflow identity, and status
  commit in the same PostgreSQL transaction.
- A committed record never changes its original or normalized text in this
  story.
- The database is authoritative; no in-memory queue is required to recover a
  case after a container restart.

**Boundary Behavior:**

- Min/Max: `normalized_text` must have at least 40 code points; text storage
  uses PostgreSQL `text` and has no implementation-added maximum.
- Empty/Null/Zero: `source_metadata` may be absent but is stored as `{}`;
  `correlation_id` may be null; all identity/text/status fields are non-null.
- Overflow/Truncation: PostgreSQL failures roll back the transaction and the
  API reports failure rather than claiming a queued document.

**Concurrency / Race-Scenario Analysis:**

- Duplicate inserts use the primary-key conflict path. The winner's immutable
  record is read before replay/conflict is returned; no lost update is allowed.

### Entity: DurableOutboxJob

Traces to: US-106 (docs/design/DESIGN.md)

| Field | Type | Unit | Constraints |
|---|---|---|---|
| `job_id` | UUID | job identity | Primary key; generated by PostgreSQL/application transaction. |
| `document_id` | PostgreSQL `text` | document identity | Required; foreign key to `intake_records.document_id`. |
| `kind` | enum | — | Required; initial value `process_document`. |
| `state` | enum | — | Required; `pending`, `claimed`, or `completed`. |
| `attempt_count` | non-negative integer | attempts | Required; starts at zero. |
| `claimed_until` | nullable `timestamptz` | UTC instant | Null when not claimed; an expired claim is recoverable. |
| `created_at`, `updated_at` | `timestamptz` | UTC instant | Required; database-generated. |

**Invariants** (must always hold true):

- Creating an intake record creates exactly one `pending` outbox job in the
  same transaction.
- A duplicate replay creates no new outbox job.
- A restarted container can rediscover every `pending` job and every expired
  `claimed` job from PostgreSQL.

**Boundary Behavior:**

- Min/Max: `attempt_count` begins at zero and cannot be negative; exact retry
  policy is owned by the later dispatcher/orchestration story.
- Empty/Null/Zero: a null `claimed_until` means pending/unclaimed; null
  `document_id`, `kind`, and `state` are invalid.
- Overflow/Truncation: job payload is represented by the referenced intake
  record, so no duplicate document text is silently truncated in the outbox.

**Concurrency / Race-Scenario Analysis:**

- A future dispatcher claims work with PostgreSQL row locking (`FOR UPDATE SKIP
  LOCKED`) and writes `claimed_until` transactionally. Competing dispatchers
  cannot claim the same job; expired claims are eligible again after restart.

### Entity: IntakeResultV2

Traces to: US-106 (docs/design/DESIGN.md)

| Field | Type | Unit | Constraints |
|---|---|---|---|
| `schemaVersion` | literal string | protocol version | Required; exactly `2.0`. |
| `requestId` | opaque string | request identity | Required; echoes the request. |
| `documentId` | opaque string | document identity | Required; canonical stored identity. |
| `caseId` | UUID string | case identity | Required. |
| `workflowId` | UUID string | workflow identity | Required. |
| `text` | UTF-8 string | Unicode code points | Required; normalized text only. |
| `language` | enum | — | Required; `tr` or `unknown`. |
| `confidence` | decimal | ratio | Required; inclusive range 0.0–1.0. |
| `ingestStatus` | enum | — | Required; initial value `queued`. |
| `warnings` | array of strings | — | Required; may be empty. |

**Invariants** (must always hold true):

- Neither original text nor internal outbox fields are returned to downstream
  services.
- A replay returns the canonical identities and normalized text from the first
  committed record.

**Boundary Behavior:**

- Min/Max: confidence accepts 0.0 and 1.0; values outside that interval are
  invalid producer output.
- Empty/Null/Zero: `warnings` may be empty; identities and normalized text may
  not be null.
- Overflow/Truncation: no response text is silently shortened by this boundary.

**Concurrency / Race-Scenario Analysis:**

- A response is constructed only after the transaction commits; a concurrent
  replay cannot observe an uncommitted case, workflow, or outbox job.

## Technology / Design Decisions

### Decision D-108: Contract migration at the existing intake route

| Option | Benefits | Drawbacks | Chosen |
|---|---|---|---|
| Upgrade the existing `/v1/ocr` contract graph to schema version `2.0` | Meets the operator decision, keeps one route, and makes the breaking change explicit. | Requires schemas, mocks, golden scenarios, callers, Docker tests, and CI checks to migrate together. | ✅ |
| Add a second `/v2/intake` route | Allows old and new callers to coexist. | Violates the operator decision not to add a second intake boundary. | ❌ |
| Mutate the `1.0` schema in place | Fewer version labels. | Violates the repository contract rule for breaking changes and makes mixed callers ambiguous. | ❌ |

**Why the first option:** The operator chose to change the current boundary,
and the repository requires a new schema version for a breaking contract.

**Why not a second route:** It creates the explicitly rejected duplicate intake
boundary.

**Why not mutate `1.0`:** Existing consumers could not distinguish the old
document shape from the new one.

### Decision D-109: Idempotency identity and conflicting replay

| Option | Benefits | Drawbacks | Chosen |
|---|---|---|---|
| Keep required `documentId` as the idempotency key; equal input replays and different immutable input rejects | Reuses the existing stable identifier and prevents duplicate cases/jobs or silent mutation. | A caller must retain its document ID to retry. | ✅ |
| Derive identity from text hash | Needs no caller identity. | Identical but distinct submissions would collapse into one case. | ❌ |
| Generate a new ID for every request | Simple server behavior. | Cannot satisfy idempotent replay after timeout/retry. | ❌ |

**Why the first option:** It is the smallest implementation consistent with
the existing contract, the approved replay requirement, and the operator's
AQ-106 resolution to reject a changed submission.

**Why not text hashing:** Content equality is not case identity.

**Why not per-request generation:** It creates a duplicate case on retry.

### Decision D-110: Minimal, source-safe normalization

| Option | Benefits | Drawbacks | Chosen |
|---|---|---|---|
| NFC normalization, line-ending normalization to `\n`, remove non-printing control characters except tabs/newlines, preserve all other text | Keeps Turkish characters and structure while removing transport/OCR noise. | Does not repair semantic OCR mistakes. | ✅ |
| Aggressive whitespace/token rewriting | May make some OCR output look cleaner. | Can change names, addresses, and legal meaning. | ❌ |
| Preserve input byte-for-byte | Simplest audit record. | Leaves invisible/control noise for downstream services. | ❌ |

**Why the first option:** It satisfies the approved normalized-text behavior
without semantic rewriting; `original_text` preserves the source for audit.

**Why not aggressive rewriting:** It could alter public-document meaning.

**Why not byte preservation only:** It fails the required safe normalization.

### Decision D-111: PostgreSQL transactional outbox

| Option | Benefits | Drawbacks | Chosen |
|---|---|---|---|
| Insert intake state and durable outbox job in one PostgreSQL transaction | Satisfies authoritative state, idempotency, and restart recovery without another required service. | Requires a database migration and dispatcher polling. | ✅ |
| Redis queue plus PostgreSQL state | Fast transient dispatch. | Adds a mandatory dependency and creates dual-write/recovery risk. | ❌ |
| In-memory background task | Minimal code. | Loses pending work on restart. | ❌ |

**Why the first option:** It directly fulfills the operator's PostgreSQL and
durable-job decision.

**Why not Redis:** Redis is explicitly optional for a future transient need.

**Why not an in-memory task:** It violates restart durability.

### Decision D-112: PostgreSQL Compose topology and verification

| Option | Benefits | Drawbacks | Chosen |
|---|---|---|---|
| Add real PostgreSQL 16 to the OCR development overlay with a named data volume and healthcheck | Reproducible real-service development without burdening baseline mock tests. | Requires the wrapper to include the OCR overlay. | ✅ |
| Add PostgreSQL to the baseline mock stack | One Compose file for every mode. | Starts unused infrastructure for deterministic contract mocks. | ❌ |
| Require an externally managed database for development | No local database image. | Makes the documented local flow non-reproducible. | ❌ |

**Why the first option:** The repository guidance adds real infrastructure only
when a real service needs it; the mock baseline remains deterministic.

**Why not baseline PostgreSQL:** Mock verification neither owns nor needs
persistent intake state.

**Why not an external database:** It conflicts with the required Docker and CI
verification path.

### Decision D-113: Changed-identity replay error

| Option | Benefits | Drawbacks | Chosen |
|---|---|---|---|
| Return HTTP 409 with the versioned standard error body, category `validation`, and `retryable: false` | Expresses an immutable-identity conflict distinctly from malformed input and preserves the established error envelope shape. | Callers need an explicit 409 path. | ✅ |
| Return HTTP 400 validation error | Reuses the baseline status for malformed requests. | Conflates a valid request with a conflicting persisted identity. | ❌ |
| Return HTTP 200 canonical record | Makes retries simple. | Silently ignores changed caller input and contradicts AQ-106. | ❌ |

**Why the first option:** A structurally valid request that would violate an
immutable stored identity is a conflict, not malformed input. The error body
remains machine-readable and non-retryable.

**Why not HTTP 400:** The client needs to distinguish a bad request from a
changed retry that needs a new document identity.

**Why not HTTP 200:** The operator explicitly chose rejection rather than
replaying changed input.
